# Setting Builder

A plain-text framework for authoring OSR (Old-School Renaissance) adventure settings as
markdown and the maps drawn from it. All "development" here is content generation
following the templates and workflow below.

This file is a map: where things live and what each part does. It is not a reference for
how any of them work. To understand a system, read the system - the authorities below are
current by construction, and any summary of them here would not be.

## Authorities

Read these rather than a description of them.

- `GENRE.md` - this build's thematic spine (era, tone, magic level, structure). Fixed;
  edited directly by the user rather than generated by a step.
- `BRIEF.md` - one KDL block: every count, mix and rate the build is built to, at
  reasonable defaults, then this setting's outline and one node per region. Templates
  and schemas set none of their own. Read by the templates
  alongside `GENRE.md`, a step reading only its scope's slice; it never overrides a schema's rules or `STYLE.md`.
  Edited directly by the user; a request in the user's own prompt carries the same weight.
- `STYLE.md` - the tests every line at every level must pass.
- `STEPS.md` - the authoritative, sequential build log. Every artifact created follows a
  numbered step here (e.g. `3d`) naming its template. Step ids grow by
  suffix and are never renumbered without explicit user request - `templates/` cite step
  ids and `tools/validate_setting.py` resolves those citations against this file (including
  its compile-list regex), so a renumber means updating both alongside every prose citation.
- `setting/Procedures.md` - what the ruleset assumes a setting provides: how a hazard is stated, Wounds, Conditions, coin and prices, time and distance, weather, encounters. A procedure that belongs to a place is a `setting/LocalProcedures.md` entry.
- `CLAUDE.md` - always loaded as system context; the rules needing active re-checking on
  every request.

## Directories

- `templates/` - one template per artifact type, each structured **Purpose / Context /
  Instructions**, and **Template** where no schema gives its shape, in folders `setting/` and
  `region/`, plus `checks/` for the judgement checks. A template is cited by its path, folder
  included. A template's Context is a KDL fence naming exactly what it reads, down to the
  members a field reads; don't pull in more than it names.
- `patterns/` - the KDL schemas, mirroring `setting/`: `Common_Schema.md` (the value
  types every field is written in), `Setting_Schema.md` (every setting file's fields),
  `Region_Schema.md` (each rating's region `seed`, `brief` and `drawn`), and one per rating
  (`Safe_Schema.md`, `Wild_Schema.md`, `Dangerous_Schema.md`) defining its location tables
  and every node they hold, shared with no other rating.
- `setting/` - the generated setting, mirroring the template set in the order STEPS.md lays
  out: setting-level artifacts, Treasure Tables I-V, the two living artifacts
  (`Procedures.md`, `Language.md`), the registries (`Lore.md`, `Keys.md`, `Quests.md`,
  `NamedCreatures.md`, `UniqueTreasures.md`, `LocalProcedures.md`), and `region/`, holding the Regional Gazetteer
  and one folder per region.
- `setting/region/[Code]/` - one region: its seed, `Seed.md`, the table files its rating's
  schema names, and one `[LocationCode].md` per location, written from the tables. Its
  brief sits beside it at `setting/region/[Code].md`, written last.
- `setting/checks/` - output of the judgement checks (STEPS.md step 5): non-mechanical
  review passes `tools/validate_setting.py` can't do, following the checklist format in
  the matching `templates/checks/*_Judgement_Check.md`. Nested under `setting/` so wiping the
  setting for a new build takes its judgement checks with it, rather than leaving them
  behind to bias the next one.
- `archive/` - the previous location-level patterns, templates and tools, and closed
  `plans/`, held for review against this build. Read by no step.
- `plans/` - proposals for framework changes not yet made: one folder per change, holding
  its `intake.md`, `spec.md` and `implementation.md`. Read by no step.
- `tools/` - exactly what content generation needs and nothing else. Stdlib-only Python, no
  package manager, no test framework beyond running these against the content.
  - `validate_setting.py` - structural linter, run in CI on every pull request.
  - `build_site.py` / `build_pdf.py` - render `setting/` into a website and a PDF, with no
    separate copy to keep in sync. Every setting table is read and drawn through
    `Setting_Schema.md`, so a table or field added there reaches both outputs unedited;
    `--check` fails a build that leaves any of it out. The site header's Roll button opens a
    3D dice overlay (`site_assets/dice-overlay.js`, on `dice.js`; three.js and cannon load from
    a CDN on first use).
  - `site_common.py` - the schema-driven readers and renderers shared by the two builders.
  - `metrics.py` - what the framework costs and how the corpus reads, counted. Judges
    nothing; the thresholds are the validator's.
  - `artgen/` - artgen's map and dungeon engines (`artgen-maps.js`, run with `node`), copied from
    `artgen-dist` `maps/` at the commit `plans/sheet-maps/brief-engines.md` records. Upgrade it by
    copying `maps/` at a newer commit, in a commit of its own.
  - `maps.py` - draws maps from the setting through artgen. `place` puts each region on its sheets
    from `BRIEF.md`'s `sheet`, `ground` and `place` lines and writes `setting/Sheets.md`. `ground` writes each
    region's `Ground.md`; `draw` writes each block's map and renders sheets, regions, blocks and cuts to SVG,
    which the site and PDF builders embed.
  - `kdl.py` - the KDL subset the location tables are written in.
  - `tables.py` - reads every region's tables and checks them against its rating's schema.
  - `templates.py` - reads each template's Context fence: what a step reads and the shape of what it writes.
  - `schema_graph.py` - reads `patterns/` as a graph of definitions, each name on a line resolved to the definition it names; `patterns.html` is drawn from it.

## Commands

```sh
python3 tools/validate_setting.py           # structural lint
python3 tools/validate_setting.py --pending [REGION]    # what each step still owes
python3 tools/validate_setting.py --location CODE       # one location's entries, and those naming it
python3 tools/validate_setting.py --read-set [STEP]     # what a step reads, per its templates' fences
python3 tools/validate_setting.py --skeleton STEP [REGION]   # the shape of what a step writes
python3 tools/validate_setting.py --brief setting|REGION # BRIEF.md as a setting or region step reads it
python3 tools/metrics.py                    # corpus, tells, budget and read-set report
python3 tools/metrics.py --tells [PATH]     # every tell hit, listed, over any markdown
python3 tools/metrics.py --carry [CODE]     # the table words each write-up carries and drops
python3 tools/build_site.py --out _site     # static site, including patterns.html
python3 tools/build_site.py --out _site --check   # ...and fail if the site omits anything setting/ holds
python3 tools/build_pdf.py --check          # the same for the PDF, without WeasyPrint
python3 -m http.server -d _site             # preview it locally
pip install -r tools/requirements-pdf.txt   # WeasyPrint, for the PDF only
python3 tools/build_pdf.py                  # single print-formatted PDF
```

`build_site.py` also renders `patterns.html`, a Schema Reference built from `patterns/`
rather than `setting/`, so it builds against an empty setting. It is a graph of every
definition - types, enums, tables, nodes, folders, regions - beside the entry for the one
selected: a line in an entry opens the definition it names, a hovered name shows it, and
Up and Back move through what was opened.

## CI and deployment

- `.github/workflows/validate.yml` - runs the validator and both `--check`s on every pull
  request and every push to `main`.
- `.github/workflows/pages.yml` - builds the site and the PDF and deploys both to GitHub
  Pages on every push to `main` touching `setting/` or the generators, or on manual
  dispatch. This needs a one-time repository setting: **Settings -> Pages -> Source:
  GitHub Actions**.
